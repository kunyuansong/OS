## 1. 实验目的、环境与证据说明

本实验理解 RISC-V 最小内核从复位到执行 C 代码的过程，掌握交叉编译、链接布局、启动栈、SBI 输出和 QEMU/GDB 远程调试方法。

| 项目目录 | `~/riscv-lab/lab1/lab1` |

## 2. Lab1 实验整体逻辑与正式练习

`lab1.docx` 中全部正式练习为：

1. **练习 1：理解内核启动中的程序入口操作。** 阅读 `kern/init/entry.S`，说明 `la sp, bootstacktop` 和 `tail kern_init` 完成的操作及目的。
2. **练习 2：使用 GDB 验证启动流程。** 跟踪 QEMU 模拟的 RISC-V 从加电到内核第一条指令，回答最初几条指令的地址与功能，并简要记录调试过程和观察结果。

文档中的现代笔记本启动流程属于拓展介绍，tmux 和内存观察属于工具介绍或实操建议，不另列为必做练习。

Lab1 的最终目标是让一个最小内核在 QEMU 模拟的 RV64 平台上运行：从 CPU 复位开始，经过固件交接，进入自己的 C 初始化函数，打印启动信息并稳定停留在无限循环。成功标准既包括输出，也包括能用 GDB 将控制流和寄存器变化对应到实际指令。

启动前，交叉编译与链接已经把源码组织成具有确定入口和内存布局的 ELF。当前 QEMU 配置加载默认固件和 `bin/kernel`；虚拟 CPU 则从 Reset ROM 的 `0x1000` 开始执行，而不是直接从 ELF 入口开始。Reset ROM 负责准备参数并跳入 OpenSBI，OpenSBI 完成平台启动所需的固件工作，再将控制权交给内核。这里必须区分“程序已装入内存”和“CPU 已开始执行程序”：链接地址与加载配置解决前者，复位跳转和固件交接解决后者。

进入 `kern_entry` 后，内核首先设置自己的启动栈，才具备执行 C 函数及其嵌套调用的基本条件。随后 `kern_init` 按链接脚本提供的边界清零 BSS，建立静态对象所需的初始状态，再调用格式化输出。输出可以在尚未实现完整设备驱动时完成，是因为 Console 将字符交给 SBI，由固件提供底层控制台服务。打印后没有调度器或其他任务可执行，也没有可返回的宿主程序，因此用无限循环保留内核控制权。这是本实验明确的结束状态，并非完整操作系统的空闲任务。

实验按“确定布局与构建 → 验证复位及固件交接 → 验证汇编入口 → 解释 C 初始化与输出”的顺序展开。各阶段分别解决代码在哪里、CPU 如何到达、C 代码如何获得栈和初始数据、如何观测启动结果的问题；后续章节将源码解释与已有实测逐一对应。

官方正式练习要求见本节列表，答案见第 5、6 节。官方报告的五项要求分别由 Markdown 文本组织、整体逻辑、核心模块分析、知识点对照和未涉及功能说明落实。提交要求为在实验项目内保存报告，并以小组 Git 仓库上传代码及报告；本项目报告位于 `notes/lab1-report.md`。

## 4. 内核构建与程序布局

### 4.1 构建流程

根据 `Makefile` 和 `tools/function.mk` 的 `listf`、`cc_template`、`read_packet` 等规则：

```text
kern 与 libs 中指定目录的 .c/.S
  → GCC 生成 obj/ 中的 .o，并生成 .d 依赖
  → ld -T tools/kernel.ld 生成 bin/kernel
  → objcopy --strip-all -O binary 生成 bin/ucore.img
```

大写 `.S` 允许预处理，入口可使用头文件宏。编译选项包括 `-mcmodel=medany -O2 -g -nostdinc -fno-builtin`，以及函数、数据分节选项；链接使用 `-m elf64lriscv -nostdlib --gc-sections`，不依赖宿主标准库，并回收未使用的节。规则还产生 `obj/kernel.asm` 和 `obj/kernel.sym`。`listf` 收集指定目录中的源文件，`cc_template` 分别建立目标文件和头文件依赖规则，`read_packet` 汇总 kernel、libs 两组对象；Make 按依赖关系决定重编译范围。交叉编译器生成目标平台指令，链接器再解析跨文件符号与重定位，因此编译成功还不等于入口地址或加载配置正确。

**实测：** 执行 `make -j1` 成功，生成 `bin/kernel`、`bin/ucore.img`；用 `readelf` 和 `nm` 确认 ELF 为 RISC-V 64，并取得：

| 符号 | 实测地址 |
|---|---|
| `kern_entry` | `0x80200000` |
| `kern_init` | `0x8020000a` |
| `bootstacktop` | `0x80203000` |

构建与 ELF 检查记录未包含完整命令参数及输出。

### 4.2 ELF 与原始镜像

| 属性 | `bin/kernel` | `bin/ucore.img` |
|---|---|---|
| 格式 | ELF 可执行文件 | 原始二进制 |
| 元数据 | 包含入口、装载信息及符号/调试信息 | 不含 ELF 头、入口及符号信息 |
| 用途 | 当前 QEMU `-kernel` 加载对象；GDB 符号来源 | 需由加载配置另行给出地址和启动安排 |

`ucore.img` 是 `objcopy -O binary` 的结果，不是带文件系统或分区表的磁盘镜像。BSS 通常不保存初始化字节，需要启动时清零；本次未提供完整 ELF 节/段表，不报告具体文件偏移或段大小。

`tools/kernel.ld` 使用 `OUTPUT_ARCH(riscv)`、`ENTRY(kern_entry)` 和 `BASE_ADDRESS = 0x80200000`。布局依次为 `.text`、`.rodata`、按 `0x1000` 对齐的 `.data`、`.sdata`、`edata`、`.bss`（含 `.sbss*`）、`end`。`ENTRY` 设置 ELF 元数据，实际 PC 转移仍需要启动链完成。`ALIGN(0x1000)` 表示 4096 字节对齐。

`.text` 保存指令，`.rodata` 保存只读常量，`.data/.sdata` 保存有初值的可写数据（本项目也把启动栈放在 `.data`），`.bss` 保存需要零初始化的对象。脚本通过 `etext`、`edata`、`end` 表达边界，使 C 初始化代码无需硬编码 BSS 长度。脚本没有用 `AT(...)` 指定另一加载地址，当前设计依赖代码在预期地址可访问；对齐和地址布局本身不建立页表，也不分配物理页。

## 5. 启动链与练习 2 解答

### 5.1 初始地址和复位指令功能

**直接答案：** 本次 QEMU 虚拟 CPU 初始 PC 为 `0x1000`。这里执行的是 QEMU Reset ROM 的短引导代码；它取得 hart ID、准备启动参数并跳转到 `0x80000000` 的 OpenSBI 固件入口。经固件初始化后，控制权交给 `0x80200000` 的 uCore 入口。这些地址和参数是本次环境实测，不是所有 QEMU 版本或所有 RISC-V 硬件的固定结果。

GDB 实测反汇编及其语义如下：

| 地址 | 指令 | 作用（根据指令与实测数据解释） |
|---|---|---|
| `0x1000` | `auipc t0,0x0` | 将当前 PC `0x1000` 放入 `t0`，作为 ROM 内数据的寻址基准 |
| `0x1004` | `addi a2,t0,40` | 得到 `a2 = 0x1028`，指向 ROM 内启动信息 |
| `0x1008` | `csrr a0,mhartid` | 读取 hart ID，本次为 `0x0` |
| `0x100c` | `ld a1,32(t0)` | 从 `0x1020` 读取 `0x87000000` 到 `a1` |
| `0x1010` | `ld t0,24(t0)` | 从 `0x1018` 读取固件入口 `0x80000000` 到 `t0` |
| `0x1014` | `jr t0` | 跳到 `0x80000000`；语义为不写返回地址的间接跳转 |

ROM 数据实测为：

| 数据地址 | 读取值 |
|---|---|
| `0x1018` | `0x80000000` |
| `0x1020` | `0x87000000` |
| `0x1028` | `0x4942534f` |

`0x4942534f` 按小端字节可解释为 `OSBI` 标识。结合启动接口语义，`a1` 可解释为设备树地址，`a2` 为固件动态启动信息指针；本次没有解析该设备树或完整信息结构，因此其完整内容不属于已验证结果。上述参数是在 ROM → 固件交接处观测的，不能直接当作内核入口参数快照。

### 5.2 实际 GDB 跟踪过程

实际执行的主要命令与观察结果如下：

1. 修复启动配置后执行 `make debug`，QEMU GDB Server 成功监听 TCP 1234。当前规则的 `-s` 提供调试端口，`-S` 暂停初始 CPU 执行。
2. 使用 `gdb-multiarch` 加载 `bin/kernel` 的符号，执行 `target remote localhost:1234` 连接 QEMU，确认初始 `pc = 0x1000`；执行 `x/8i $pc` 查看复位位置附近的指令，其中前六条复位指令如第 5.1 节所示，并读取上表数据。
3. 连续执行五次 `si`，单步执行前五条指令，取得 `pc = 0x1014`、`t0 = 0x80000000`、`a0 = 0x0`、`a1 = 0x87000000`、`a2 = 0x1028`。
4. 再执行一次 `si`，执行 `jr t0` 后，`pc = 0x80000000`，实际进入 OpenSBI 固件入口。
5. 执行 `hbreak *0x80200000` 设置硬件断点，再执行 `continue`，成功命中 `kern_entry`，验证固件最终交接到内核。
6. 在入口用 `x/8i $pc` 查看指令，再用 `si` 逐条验证栈初始化与尾跳转，具体结果见练习 1。
7. 执行 `continue` 继续运行，QEMU 输出 `(THU.CST) os is loading ...`；暂停后 `pc = 0x8020003a`，对应 `j 0x8020003a`，确认最终忙循环。

这条跟踪链验证了 ROM、固件入口、内核入口及内核输出。OpenSBI 内部阶段采用继续运行至断点的方法，**没有逐条跟踪其全部初始化指令**。

```text
0x1000：Reset ROM（准备启动参数）
  → 0x80000000：OpenSBI（固件初始化与交接）
  → 0x80200000：kern_entry（建立内核栈）
  → 0x8020000a：kern_init（清零、输出）
  → 0x8020003a：无限循环
```

指导文档 tips 将复位处概括为 OpenSBI，并建议通过 watch 观察“固件加载内核”。本次应更精确地区分 Reset ROM 与 OpenSBI：内核由 QEMU 启动加载配置预先装载，固件负责交接；没有证据证明 OpenSBI 执行了内核镜像复制。该 watch 验证未执行。

## 6. 练习 1 解答：建立栈并进入 C 内核

`kern/init/entry.S` 的核心代码：

```asm
kern_entry:
    la sp, bootstacktop
    tail kern_init

.section .data
    .align PGSHIFT
bootstack:
    .space KSTACKSIZE
bootstacktop:
```

### 6.1 `la sp, bootstacktop`

**直接答案：** 将 `bootstacktop` 的地址放入栈指针 `sp`，为后续 C 函数的栈帧、局部变量及寄存器保存提供内核栈。它取得地址，不读取该地址处的内容。

`kern/mm/mmu.h` 定义 `PGSIZE = 4096`、`PGSHIFT = 12`；`memlayout.h` 定义 `KSTACKPAGE = 2`，故 `KSTACKSIZE = 8192`。`.align PGSHIFT` 在此 RISC-V 汇编中要求 4096 字节对齐，`.space` 在 `.data` 预留栈区。栈区为 `[bootstack, bootstacktop)`，初始栈指针位于高地址端，按调用约定向低地址增长，并满足 16 字节栈对齐。

`la` 是伪指令，实际展开受链接与松弛影响。本次反汇编为：

```asm
0x80200000: auipc sp,0x3
0x80200004: mv sp,sp
```

`auipc` 计算 `0x80200000 + (0x3 << 12) = 0x80203000`；后面的 `mv sp,sp` 是零偏移地址形成操作的反汇编显示，语义等价于 `addi sp,sp,0`，值不变。不能把这一具体展开推广为所有 `la` 的固定展开。

| 时刻 | `sp` 实测值 |
|---|---|
| 执行 `la` 前 | `0x80017ee0` |
| 执行 `auipc sp,0x3` 后 | `0x80203000` |
| 执行 `mv sp,sp` 后 | `0x80203000` |

前一个值是进入内核时继承的上下文，本次入口将其替换为自己的栈顶。由栈顶和栈大小可推导栈起点为 `0x80201000`，该起点不是已有记录中的独立符号测量值。

### 6.2 `tail kern_init`

**直接答案：** 将控制权交给不返回的 `kern_init`，使用已建立的栈继续初始化；尾跳转不为当前入口建立新的 `ra` 返回地址。一般尾调用伪指令可采用 PC 相对地址形成与间接跳转，本次最终链接结果简化为直接跳转：

```asm
0x80200008: j 0x8020000a <kern_init>
```

`j` 表示不保存链接地址的跳转（语义为 `jal x0,目标`；具体编码可由压缩指令实现）。本次地址间隔表明该跳转占 2 字节。

| 寄存器 | 执行前 | 执行后 |
|---|---|---|
| `pc` | `0x80200008` | `0x8020000a` |
| `sp` | `0x80203000` | `0x80203000` |
| `ra` | `0x800078cc` | `0x800078cc` |

`ra` 保持原值是本次单步确认的事实，并非入口主动设置的返回点。`kern_init` 声明为 `noreturn` 且最终无限循环，因此无需返回汇编入口。后续 C 函数执行可能调整 `sp`，上表只说明尾跳转本身的效果。一般未松弛的 `tail` 可通过 `auipc` 配合 `jalr x0` 形成跳转，最终应以链接后反汇编为准。入口没有设置 `gp`、页表或异常向量，也没有分配多核独立栈；当前实现仅完成进入 C 所需的启动栈与控制转移。

## 7. `kern_init`：清零、输出和无限循环

`kern_init` 是汇编入口之后的 C 初始化入口，负责把最小运行环境转换为可观测的启动结果。当前函数只执行清零、输出和循环，没有调用 `cons_init`、内存管理器或中断初始化。其核心代码位于 `kern/init/init.c`：

```c
int kern_init(void) __attribute__((noreturn));
int kern_init(void) {
    extern char edata[], end[];
    memset(edata, 0, end - edata);
    const char *message = "(THU.CST) os is loading ...\n";
    cprintf("%s\n\n", message);
    while (1)
        ;
}
```

**源码推导：** `edata`、`end` 来自 `tools/kernel.ld`，是地址边界符号，声明不会另外分配数组。`memset` 清零 `[edata, end)`，覆盖 BSS 及可能的前置对齐填充，以满足未显式初始化静态存储对象的零初始化要求。`libs/string.c::memset` 的默认实现用指针逐字节写入指定值并返回起始指针；本项目没有定义 `__HAVE_ARCH_MEMSET`，因此使用该通用实现。内核不能依赖宿主 C 标准库完成这项工作，Makefile 的 `-fno-builtin` 也使该调用使用项目提供的实现；启动栈在 `.data`，位于此清零范围之前，不会被该操作清除。本次没有提供清零前后的内存快照，也没有给出 BSS 实际长度。

输出消息经 `%s` 格式化。消息自身含一个 `\n`，格式串再追加两个，故源码预期末尾共有三个换行，不输出字符串终止符；实测确认可见启动文本，未单独统计换行字节。

`while (1)` 是持续执行的忙循环，没有 `wfi`、关机或进程退出操作。**实测：** 暂停后 `pc = 0x8020003a`，指令 `j 0x8020003a`，与源码一致。`noreturn` 告知编译器函数不返回，真正阻止返回的是控制流中的无限循环。

## 8. SBI 字符输出调用链

```text
kern_init
  → cprintf → vcprintf → vprintfmt → cputch
  → cons_putc → sbi_console_putchar → sbi_call
  → ecall → OpenSBI 控制台服务 → 返回调用链
```

`kern/libs/stdio.c::cprintf` 组织可变参数，`vcprintf` 将 `cputch` 和计数器交给 `libs/printfmt.c::vprintfmt`。格式解析器对普通字符直接回调，对 `%s` 逐字符读取字符串并回调。`cputch` 调用 `cons_putc` 并递增计数；该计数代表尝试输出的字符数，不是硬件成功发送的确认。

格式化模块把“字符串如何表示”与“字符如何发送”分开，使内核可以在没有宿主标准输出的环境下使用 `cprintf`。当前 `vprintfmt` 还支持字符、整数、指针等格式及宽度、精度处理，但本实验运行记录只验证了启动消息所用的 `%s` 路径，不能据此宣称与标准库 `printf` 完全等价。

`kern/driver/console.c::cons_putc` 将字符转换为 `unsigned char`，交给 `libs/sbi.c::sbi_console_putchar`。后者调用 `sbi_call(SBI_CONSOLE_PUTCHAR, ch, 0, 0)`，其中服务号为 1。核心内联汇编意图为：

```asm
mv x17, %[sbi_type]    # a7：服务号 1
mv x10, %[arg0]        # a0：字符
mv x11, %[arg1]        # a1：0
mv x12, %[arg2]        # a2：0
ecall
mv %[ret_val], x10     # 从 a0 取得返回值
```

这是 legacy SBI 字符输出接口形态。S 模式内核通过环境调用请求固件服务，由固件完成底层控制台输出，内核此路径没有直接写 UART 寄存器。**实测**启动字符串成功输出，支持此输出路径在当前构建中可用；**源码推导**给出其分层机制，未逐条调试 `ecall` 陷入、固件串口操作或返回过程。

Console 提供统一字符接口，使上层不必了解固件调用寄存器。当前 `cons_init`、`kbd_intr`、`serial_intr` 都为空，启动输出依赖已可用的固件服务；输入路径虽有 `cons_getc` 和 `sbi_console_getchar` 声明，仓库没有后者的定义，因此本实验只证明输出可用。`libs/sbi.h` 中其他服务声明及 `sbi_set_timer` 包装同样不代表对应的内核管理功能已实现。

从特权机制看，此处的 `ecall` 是 S 模式内核请求 M 模式固件服务的环境调用；用户态系统调用则是用户程序请求内核服务，调用双方、权限边界和接口均不同。此机制解释依据源码与固件交接日志，具体陷入与返回的 CSR 变化没有单步记录。

## 9. 原 Makefile 启动问题：定位、修复与验证

实验原先使用的配置为：

```make
-device loader,file=$(UCOREIMG),addr=0x80200000
```

**实测现象：** OpenSBI 显示 `Domain0 Next Address = 0x0`，未观察到内核启动消息。ELF 的入口和符号检查已确认内核入口为 `0x80200000`，因此需要检查装载配置与固件下一阶段地址的交接，而不能仅凭没有输出判断 C 内核有错误。

**定位解释：** 将镜像放到指定内存地址，与向启动链提供下一阶段入口信息是两个环节。本次 loader 配置没有产生正确的 OpenSBI Next Address。现有记录没有深入审计 QEMU/OpenSBI 内部实现，故不将此现象归结为所有版本的 loader 必然失败，也不宣称已证实具体内部参数生成错误。

实验中已将 `qemu`、`debug` 两个目标改为加载 ELF：

```make
$(V)$(QEMU) \
    -machine virt \
    -nographic \
    -bios default \
    -kernel $(kernel)
# debug 目标另加 -s -S
```

当前 Makefile 中的启动规则与上述修复一致。两目标仍依赖 `$(UCOREIMG)`，但启动实际传入的是 `$(kernel)`，即 `bin/kernel`；`SWAPIMG`、`SFSIMG` 在当前文件中没有定义，不能据此声称构建了交换区或文件系统镜像。

| 验证项 | 已记录的实测结果 |
|---|---|
| `make qemu` | 启动成功，打印内核消息 |
| OpenSBI 下一阶段地址 | `Domain0 Next Address = 0x80200000` |
| OpenSBI 下一阶段模式 | `Domain0 Next Mode = S-mode` |
| `make debug` | QEMU GDB Server 启动成功，TCP 1234 监听正常 |
| 内核入口断点 | 命中 `0x80200000` 的 `kern_entry` |

日志表明固件配置为交接到 S 模式，断点验证实际到达内核；未提供内核入口特权状态 CSR 的独立读取。Makefile 的 `gdb` 目标仍硬编码 `riscv64-unknown-elf-gdb`，而实际使用 `gdb-multiarch`，不将两者混写为同一条已执行命令。

## 10. 实验知识点与 OS 原理的联系及差异

| 知识点 | OS 原理中的一般概念 | 本实验的对应实现、联系与局限 |
|---|---|---|
| CPU 复位与启动 | 复位使 CPU 从平台规定的初始状态执行引导代码，逐步建立 OS 运行环境 | 本次从 `0x1000` 的 Reset ROM 开始，经固件进入内核；这是虚拟平台的具体启动路径，复位地址不能推广到所有硬件 |
| Bootloader、固件与内核 | 引导程序通常负责选择、加载及交接 OS；固件提供平台初始化或运行时服务；内核负责资源管理 | 本实验由 QEMU 加载配置承担镜像装载，Reset ROM 和 OpenSBI 完成启动交接，OpenSBI 继续提供 SBI 服务；没有独立的磁盘 Bootloader，内核也尚无资源管理能力 |
| RISC-V 特权级与 SBI | M 模式管理机器级资源，S 模式运行内核，U 模式运行用户程序；跨权限服务需明确接口 | 日志给出下一阶段为 S-mode，内核通过 SBI `ecall` 请求固件输出；没有用户程序或用户态系统调用，入口特权 CSR 未独立读取 |
| 内核入口与调用约定 | PC 决定执行位置，SP 指向栈顶，RA 保存普通调用的返回地址；C 函数依赖栈对齐及寄存器约定 | `la` 设置内核栈，`tail` 改变 PC 而保持 SP、RA；这里只建立单个启动上下文，没有进程栈切换，伪指令展开以本次反汇编为准 |
| ELF、链接与加载 | 链接确定符号和重定位，ELF 描述入口及可加载内容，加载器把内容放到目标内存后交接执行 | `kernel.ld` 布局内核，QEMU 加载 `bin/kernel`，GDB 使用其中符号；原始镜像不含 ELF 元数据，链接地址也不等于建立了虚拟映射 |
| BSS 与运行环境 | 静态存储对象的零初始化需要由加载或启动环境保证，不能由源代码声明自动完成 | 本内核用链接边界和自己的 `memset` 清零；启动栈位于清零区之前。该逻辑经源码核对，但没有 BSS 前后快照 |
| 控制台与设备驱动 | 驱动屏蔽设备细节，上层通过统一接口进行 I/O；完整驱动还需初始化、缓冲与中断处理 | `cprintf`、Console、SBI 分层协作，固件执行底层输出；当前没有内核直接管理的完整 UART 驱动，输入和中断路径不完整 |
| 最小内核与完整 OS | 完整 OS 在保护机制下管理内存、进程、设备并向应用提供服务 | 本实验只具备启动、初始化和输出，末尾忙循环用于保持控制权；它不是任务调度或低功耗空闲机制 |

GDB 的断点、单步和寄存器检查将上述概念与实际执行联系起来，但证据范围仍由观测位置决定。例如入口断点能证明固件交接到内核，不能证明 OpenSBI 的全部内部初始化都经过审计。

## 11. 当前实验尚未涉及的重要 OS 功能

| 功能 | 在完整 OS 中的作用 | 当前最小内核为何不具备 |
|---|---|---|
| 物理内存管理 | 跟踪可用物理页、分配与回收内存，避免内存冲突 | 只有页大小与静态栈宏，没有空闲页结构或分配器 |
| 虚拟内存与页表 | 建立地址映射、访问权限和进程地址空间隔离，配合缺页处理 | 入口没有建立页表或配置地址转换，没有映射管理和缺页处理代码 |
| 中断与异常处理 | 响应时钟、设备事件及同步异常，保存现场并执行处理程序 | 没有内核陷阱入口、异常分派及现场恢复逻辑；SBI 调用由固件处理不等于内核已实现陷阱系统 |
| 进程与线程 | 表示独立执行实体，管理资源、生命周期和执行上下文 | 只有单一启动控制流，没有进程控制块、线程创建或独立执行栈管理 |
| 进程调度 | 从可运行任务中选择执行者，实现 CPU 共享和公平性 | 没有任务队列、调度策略或时间片，忙循环不会切换任务 |
| 上下文切换 | 保存和恢复寄存器、栈及必要的地址空间状态，以继续不同任务 | 入口只一次性设置 SP，未提供上下文保存、恢复或切换函数 |
| 用户态与系统调用 | 用权限隔离保护内核，并向用户程序提供受控服务入口 | 没有 U 模式程序、用户地址空间或内核系统调用分派；现有 SBI 是内核与固件之间的接口 |
| 文件系统 | 用文件、目录及元数据组织持久化数据，支持读写与权限管理 | 没有文件或目录操作、缓存和块设备管理，`ucore.img` 是裸内核镜像 |
| 完整设备驱动 | 管理设备初始化、输入输出、缓冲、中断和错误处理 | 字符输出依赖固件，Console 初始化及中断函数为空，输入服务定义缺失 |
| 多核调度与同步 | 启动多个执行核，分配任务，以锁或其他机制保护共享状态 | 记录只验证当前 hart 的启动，源码没有每核独立栈、跨核调度或同步机制；SBI 服务号与声明不构成这些能力 |

这些功能都需要在最小启动环境之上建立额外的数据结构和控制机制。当前能打印启动消息，只能说明启动与输出链可用，不能据此推断上述功能已经实现。

## 12. 实验总结与证据边界

实验记录与当前源码一致：构建产生 RISC-V 64 位 ELF 和原始镜像；Reset ROM 将控制权交给 OpenSBI，固件最终到达 `kern_entry`；入口把 `sp` 设置为 `0x80203000`，不改写 `ra` 地跳入 `kern_init`；启动文本成功输出，最终停留在 `0x8020003a` 的无限循环。原 loader 配置的下一阶段地址问题，在本环境中通过 `-kernel $(kernel)` 修复并获得运行和断点验证。

以下项目仍未验证，不影响两道正式练习已有的直接答案，但不能据此扩大结论：

- 未逐条跟踪 OpenSBI 内部初始化，未解析完整动态启动信息或设备树；未独立读取内核入口特权状态 CSR。
- 未给出完整 ELF 节/段表、BSS 边界和清零前后快照，也未逐字符统计输出换行。
- `libs/sbi.c::sbi_call` 直接改写 `a0/a1/a2/a7`，却仅声明 `memory` clobber，普通 `r` 输入约束存在潜在寄存器分配风险；本次输出成功，不能将风险写成已发生错误，仍需专门审计生成代码及约束。
- `sbi_console_getchar` 的实现缺失、`gp` 相关访问是否安全等旧笔记疑点未专项验证；成功链接和输出不代表未使用路径也可用。
- 跨 QEMU 版本行为不在本次验证范围内。

本实验的主要认识是：内核启动需要依次解决装载与交接、调用环境和初始数据状态，之后才能通过分层接口得到可观测结果。两道练习分别验证入口对执行上下文的建立，以及复位到内核的控制流；源码与实测相互印证，使“能打印一行文字”成为对启动链的具体验证。
