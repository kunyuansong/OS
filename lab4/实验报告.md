## 二 对实验整体逻辑线的理解

我们把本实验理解为依次回答三个问题：线程依靠什么内存环境运行，线程的初始运行状态怎样构造，以及 CPU 怎样从一个线程交给另一个线程。这三个问题分别对应本次的三个功能部分，前一部分提供后一部分成立的条件。

首先，需要有可靠的物理页分配和地址映射。PCB 使用 `kmalloc` 获取内存，线程内核栈使用连续的物理页，因此 lab2 的物理内存初始化和 best-fit 分配器必须先可用。启动汇编提供的 1 GiB 粗粒度映射只能帮助内核进入高地址空间，还不能表达代码只读可执行、只读数据不可写、普通数据可写等差异。因此，在物理页管理可用后，新建 4 KiB 粒度的三级页表，建立精细映射，再切换到新页表。VMA 模块进一步提供逻辑地址区间的描述和查找，但本实验不据此执行按需缺页分配。

其次，线程需要可以由调度器管理的身份和运行现场。`proc_struct` 将状态、PID、父线程、内核栈、页表地址、上下文和中断帧联系起来。idle 线程并不是从零启动的新函数，而是把已有内核启动执行流纳入线程管理；init 则是第一个通过通用创建流程分配独立内核栈并构造初始现场的线程。只有线程资源与现场全部准备完毕，才能将其发布到进程链表和 PID 哈希表中，并设置为可运行。

最后，调度器选择线程，上下文切换机制执行选择结果。`schedule` 决定“接下来运行谁”，`proc_run` 完成当前线程指针、页表及切换环境的准备，`switch_to` 才真正保存和恢复 CPU 寄存器。新线程第一次被选中时，还没有可以返回的旧调用链，因此通过预先设置的 `forkret`、中断帧与 `sret` 路径进入指定入口函数。以后被切回时，则沿保存的返回地址继续执行。

启动过程在 `kern/init/init.c` 中体现为：

```text
启动汇编建立临时映射并跳到高地址
  → kern_init 清零 BSS 并解析设备树
  → pmm_init 初始化物理页管理 建立新页表并检查映射
  → idt_init 设置异常入口
  → vmm_init 检查地址区间管理
  → proc_init 建立 idle 和 init
  → clock_init 设置时钟并开启中断
  → cpu_idle 根据 need_resched 进入 schedule
  → proc_run 和 switch_to 切换到 init
```

这里要区分“具备时钟中断”和“实行时钟抢占”。本实验虽然初始化了时钟，但普通线程并不是每隔一个时间片就自动被抢占。idle 在调度标志置位时让出 CPU，评分中的两个测试线程通过主动调用 `schedule` 验证轮转。这是单核、协作式的线程调度。

## 三 第一部分 页表与内存映射

**完成者：2411241 宋坤远。**

### 3.1 物理页与页表的关系

物理内存分配器管理的是页框，页表管理的是虚拟地址到页框的映射。同一个物理页可以被多个虚拟地址映射，因此不能仅依据一次映射移除就释放物理页，必须维护映射引用计数。这里的引用计数指受相应接口管理的引用，不能理解为 CPU 每次访问页面都会增加一次计数，也不能把启动阶段所有直接映射都视为由 `page_insert` 建立的引用。

本工程的物理内存从 `0x80000000` 开始，`npage` 表示物理地址上界对应的页号，而不是从内存起点开始计算的实际页数。描述符下标为 `PPN(pa) - nbase`。承接 lab3 的 `page_init` 使用当前 `sizeof(struct Page)` 计算描述符占用，避免 lab4 扩充描述符后仍按旧大小预留空间。固件、内核、描述符和对齐占用的区域保留，剩余完整页面才交给分配器。

### 3.2 get_pte 和 get_page

Sv39 将地址按三级索引和页内偏移拆分。`get_pte` 通过 `PDX1`、`PDX0` 和 `PTX` 定位最终一级页表项。中间页表项保存下一级页表的物理地址，内核需要转换为可以访问的高地址指针后继续遍历。

当 `create` 为假时，查找不得消耗物理页；需要的中间页表不存在便返回 NULL。当允许创建时，新页表页被清零，引用数设置为 1，再把非叶子项指向它。如果本次新建第一层后，继续分配下一层失败，就撤销并释放本次创建的第一层，避免失败调用留下无用页表。

当前 walker 只管理 4 KiB 叶子。遇到原有大页叶子时返回 NULL，防止将数据页误解释成页表。内核精细映射因此采用新建根表的方式，而不是在原 1 GiB 叶子下继续遍历。

`get_page` 基于 `get_pte` 的只读查找取得物理页描述符；有需要时通过 `ptep_store` 一并返回页表项地址。它不负责分配页面或新增映射。

### 3.3 page_insert 的三种正常情况

`page_insert` 首先取得最终页表项，取得失败时返回 `-E_NO_MEM`，不增加目标页引用。成功找到页表项后，需要区分三种情况。

原地址没有有效映射时，为目标页增加一个引用并建立映射。原地址映射不同页时，减少旧页引用，在旧页无引用时释放它，再建立目标映射。原地址已经映射目标页时，只更新权限，最终引用计数保持不变。

同页重映射是最容易遗漏的情况。实现先为新页增加引用，再识别旧页与新页是否相同；相同时抵消新增引用。这样既避免多算一次引用，也避免在“先删除旧映射”的处理中把仍要使用的页面提前归还分配器。权限变化同样需要刷新 TLB，否则 CPU 可能继续使用缓存中的旧权限。

本工程将 `perm=0` 解释为只读叶子映射，带 W 时同时补 R，仅有 X 的映射仍可保留执行权限。这样做是为了适配 Sv39 叶子项的编码约束；不能把只置 V、没有 R/W/X 的项当作普通数据页叶子。代码还预置 A，写页预置 D，符合本实验预映射且不实现 A/D 缺页处理的范围。

### 3.4 撤销映射与分配映射

`page_remove_pte` 处理已经定位的有效叶子项：减少物理页引用，零引用时归还物理页，清空页表项并刷新对应地址的 TLB。它不自动回收中间页表；因此移除数据页后，仍有页表页占用内存不等于数据页泄漏。

`page_remove` 使用不创建页表的查找，找到后才调用上述内部函数。重复移除或移除不存在的映射应保持资源状态不变。

`pgdir_alloc_page` 组合物理页分配与映射两个步骤。如果前者成功而后者失败，要归还刚取得的数据页；仅返回 NULL 而不回收会使错误路径逐次消耗物理内存。此接口不承诺自动清零新分配的数据页。

### 3.5 内核分段预映射与 VMA 管理

`pmm_init` 在基础页表检查结束后分配新根表，并分别映射代码段 RX、只读数据段 R，以及数据、BSS 和剩余可管理内存 RW；这些内核叶子均不设置 U。链接脚本将段边界按页对齐，否则共享同一页的代码和可写数据无法同时满足各自的权限要求。切换 `satp` 之前，当前代码、内核栈和新页表必须都已经可访问。

`vmm.c` 是已有的逻辑地址区间管理框架。`mm_create` 创建管理结构，`vma_create` 描述半开区间 `[vm_start, vm_end)`，`insert_vma_struct` 按起始地址有序插入并检查相邻区间不重叠，`find_vma` 优先检查缓存，再遍历链表，`mm_destroy` 释放 VMA 和管理结构。其作用是描述“哪些区间合法、具有什么逻辑属性”，并不等同于硬件页表翻译。当前内核线程的 `mm` 为 NULL，不会因此拥有独立用户地址空间；`mm_destroy` 也不能被当作完整页表与用户物理页回收函数。

## 四 第二部分 内核线程创建

**完成者：2410949 何翔。**

### 4.1 alloc_proc 与线程控制块

`alloc_proc` 用 `kmalloc` 分配 PCB，并完整初始化。新 PCB 的状态为 `PROC_UNINIT`，PID 为 -1，尚不具备可被调度的身份。`mm`、父线程指针、中断帧、计数、名称、标志和上下文等先置为初始值；两个链表节点分别初始化。`pgdir` 保存已经建立的内核根页表的物理字节地址。

“完整初始化”不仅为了使字段容易观察，也保证失败路径、哈希查找和后续调度不会读取上一次内存使用者留下的内容。线程名称复制使用有长度限制的 `strncpy`，配合事先清零的名称数组，避免从短字符串固定读取 15 字节。

### 4.2 内核栈和地址空间

`setup_kstack` 为普通新线程分配两页连续内存作为内核栈；`put_kstack` 在创建失败时归还它。独立内核栈是不同线程保存各自函数调用链的基础，即使线程共享内核地址空间，也不能共用同一运行栈。

`copy_mm` 在本实验中不执行用户内存复制。它确认当前线程 `mm == NULL`，使新线程的 `mm` 仍为 NULL，并共享内核页表。这反映本实验仅创建内核线程的边界，不代表一般进程创建不需要处理地址空间。

### 4.3 copy_thread 与初始现场

`copy_thread` 在新栈顶部保留一个完整 `trapframe`，把模板复制到该位置。帧必须属于新线程，不能让 `proc->tf` 指向 `kernel_thread` 函数的局部变量，否则函数返回后该地址就不再可靠。

子线程帧中的 a0 设为 0。传入的栈参数为零时，帧中恢复后的 sp 指向新内核栈顶；非零时按接口使用指定的栈地址。`context.ra` 指向 `forkret`，`context.sp` 指向中断帧所在地址。这里有两个不同的栈状态：第一次切换到 `forkret` 时使用的是 context 中的 sp；随后异常返回恢复的才是 trapframe 中的 sp，二者不能混用。

`kernel_thread` 构造清零模板，在 s0 中放入口函数，在 s1 中放参数，epc 指向 `kernel_thread_entry`。status 设置 SPP 和 SPIE，同时清除 SIE，使首次 `sret` 返回到 S-mode，并按返回语义恢复中断使能。它调用 `do_fork` 创建线程，不在父线程的调用栈上直接执行目标函数。

### 4.4 do_fork 的资源与发布顺序

`do_fork` 的顺序为检查数量上限、分配 PCB、记录父线程、分配栈、准备内存管理、复制线程现场，然后在中断保护区内分配 PID、加入哈希表和进程链表、增加数量并唤醒线程。

这个顺序使调度器只能观察到初始化完整的可运行线程。创建顺序也影响调度顺序：新线程插入链表尾部，从 idle 扫描时就按创建先后获得机会。

错误处理需要与资源获得过程对应。达到 `MAX_PROCESS` 返回 `-E_NO_FREE_PROC`，不分配资源；PCB 或栈分配失败返回 `-E_NO_MEM`，释放已经取得的资源；后续内存准备若失败，则先释放栈再释放 PCB。当前 `copy_mm` 在限定条件下直接成功，但保留回收分支使创建流程的资源责任仍然明确。

### 4.5 proc_init 中的 idle 与 init

idle 将启动以来的当前执行流包装成 pid 为 0 的线程。它使用已有 `bootstack`，不重新分配栈，初始 `tf` 为 NULL、`runs` 为 0，`need_resched` 置为 1，使完成初始化后能尽快调度。idle 不加入普通进程链表，避免与调度器的空闲保底角色混淆。

设置 `current=idleproc` 后，`proc_init` 调用 `kernel_thread` 创建 `init_main`，取得 pid 为 1 的线程，并命名为 init。init 的父线程为 idle，拥有独立内核栈，但共享内核地址空间。PCB 分配与线程创建的区别由此体现：获得一个 PCB 只是开始，拥有完整现场并进入可运行状态才是创建完成。

## 五 第三部分 线程切换与调度

**完成者：2413121 林科融。**

### 5.1 schedule 决定运行对象

`schedule` 首先保存并关闭中断，清除当前线程的 `need_resched`。当前线程是 idle 时，从 `proc_list` 表头开始查找；当前线程是普通线程时，从其后继开始循环扫描。扫描跳过链表头节点，以及不处于 `PROC_RUNNABLE` 的线程。

若没有其他线程可运行，但当前普通线程仍然可运行，循环可以再次选中它；只有找不到普通可运行线程时才回到 idle。空链表也需要正确终止，不能把表头当成 PCB 或无限循环。被选中线程的 `runs` 增加，目标与 current 相同时不执行实际切换。这个字段记录调度选中次数，不能解释成运行时间或已经完成的时间片数。

该调度器按链表次序循环选择，可理解为简化的协作式轮转。它没有优先级、时间片耗尽处理或抢占保证，所以不能直接等同于完整的抢占式 Round-Robin 调度器，也不应仅因新线程按顺序入链就将其理解为严格的一次性 FIFO 执行。

### 5.2 proc_run 切换线程环境

`proc_run` 先判断目标是否已经是当前线程。真正需要切换时，在中断保护区内保存旧 PCB 指针、更新 current，把目标页表编码为 Sv39 的 `satp` 值，刷新 TLB，再调用 `switch_to`。

`pgdir` 是物理字节地址，而 satp 的页表根字段需要物理页号，因此编码为 `MODE=8` 和 `pgdir >> PGSHIFT` 的组合。把页表的虚拟指针或未移位的物理字节地址直接写入 satp 都不能建立正确翻译。本实验内核线程使用相同根表，所以切换时并没有真正获得彼此隔离的用户地址空间，但接口已经给后续进程切换保留位置。

### 5.3 switch_to 保存和恢复上下文

`switch.S` 按 `struct context` 的顺序处理 ra、sp、s0 至 s11，共 14 项；RV64 下每项 8 字节，偏移从 0 到 104 字节。a0 和 a1 分别指向旧、新上下文，汇编保存和加载期间不能破坏它们的寻址作用。

保存 ra 决定旧线程未来从哪里继续，保存 sp 保留其函数调用栈，保存 s0 至 s11 则遵守被调用者保存寄存器约定。由于切换在 C 函数调用边界发生，调用者负责处理跨调用仍然存活的 caller-saved 值，因此 context 不需要像异常中断帧一样保存全部通用寄存器。异常可以打断任意指令，与显式函数调用的约束不同，这也是 trapframe 与 context 必须分开的原因。

中断保护不是简单地在切换后无条件开中断。每个调用现场保存进入前的中断状态；线程未来被切回并沿原调用链返回时，才恢复属于该现场的状态。这使嵌套的 `schedule` 和 `proc_run` 保护可以保持一致。

### 5.4 第一次执行与以后继续执行的区别

新线程的 context 没有来自历史执行的返回地址，因此创建时人为设置首次入口。实际路径为：

```text
switch_to 恢复新 context 并 ret
  → forkret
  → forkrets(current->tf)
  → 将 sp 设为新 trapframe 并进入 __trapret
  → 恢复状态寄存器 通用寄存器和最终 sp
  → sret 跳到 tf.epc 即 kernel_thread_entry
  → 把 s1 作为 a0 参数 调用 s0 中的线程函数
  → 函数返回后进入 do_exit
```

已有线程再次被恢复时，不会重复创建初始帧或重走线程入口，而是从之前 `switch_to` 的返回位置继续执行。本实验 `do_exit` 仍保留骨架的 panic，尚未实现僵尸状态、父线程唤醒和资源回收，所以 init 输出后进入内核监视器属于当前范围的预期路径。

## 六 三个练习的 spec 与 prompt 组织

我们按照“一个具有完整状态变化和错误回收责任的模块一个提示词”划分任务，而不是把整个实验一次性交给 AI，也不把紧密关联的初始化和错误回收函数完全割裂。

`[PROMPT]` 写清目标文件、修改范围和输出要求，要求直接修改真实文件；`[RELY]` 只提供当前工程中真实存在的字段、宏和可调用接口；`[GUARANTEE]` 列出必须交付的函数签名；`[SPECIFICATION]` 用 Pre-Condition、Post-Condition、Case 和 Requirements 描述可检查的行为约束。spec 关注正常和失败后系统应满足什么条件，代码实现再决定具体步骤。

第一部分的 spec 围绕映射与引用守恒组织，重点区分新映射、替换映射、同页重映射和内存不足。第二部分围绕创建事务组织，重点是初始化完成再发布、独立栈和帧、失败不泄漏。第三部分围绕可恢复的执行现场组织，重点是扫描终止、只选择可运行线程、C 与汇编布局一致以及中断状态正确恢复。

下面按最终接口整理三个可复现的主要提示词，包含各练习的函数规格；它们是对实验需求和实现约束的归纳，不作为逐字历史聊天记录。项目已有 `PROMPTS.md` 还保留了开发阶段使用的未署名约束和故障定位提示词；本次提交的完成者以本报告和 LAB4 代码注释为准。

## 七 AI 辅助实现中的问题与解决过程

我们在使用 AI 时，先用规格限定接口和资源责任，再检查真实代码，最后用宿主机逻辑检查及虚拟机运行验证。问题不能都归因于 AI 生成函数本身：本次既遇到实际的构建和评分故障，也在审查中修正了继承框架的兼容性问题。下面分别说明，避免把没有实际触发的风险写成已经观察到的运行 bug。

### 7.1 实际故障 文件时间在未来导致反复警告

虚拟机最初执行 make 时，反复出现 `tools/function.mk has modification time ... in the future`，时间差约为七小时。刷新 `kern`、`libs`、`tools` 和 Makefile 的时间后可以构建，但第一次评分复制工程时，tar 仍对 Markdown 和配置文件给出未来时间警告。

原因是工程文件时间与虚拟机当前时间不一致，而第一次处理只覆盖了编译输入，没有包含全部文档。最终在工程目录刷新所有普通文件的时间，再重新构建：

```bash
find . -type f -not -path './.git/*' -exec touch {} +
make clean
make -j2
```

这一处理没有修改代码内容。它说明跨机器复制后，构建问题也可能来自环境元数据，不能仅凭 make 警告判断内核实现错误。

### 7.2 实际故障 普通启动正常但评分为 0/30

普通 `make qemu` 已完成页表和 VMA 检查，init 也正常输出；随后旧评分脚本却对三项都打印 `no $qemu_out` 并给出 0/30。此前编译和链接已经完成，因此这不是三项断言均已执行并失败的证据，而是评分没有得到有效串口日志。

检查脚本发现，它用 `-S` 暂停 QEMU，再依赖 GDB 下断点并继续运行；GDB 的标准输出和错误全部被丢弃，而 GDB 返回后会立即结束 QEMU。这使调试连接或继续执行失败时，脚本可能在内核尚未运行前就停止虚拟机。由于当时没有保存旧 GDB 错误输出，不能进一步断言具体是 GDB 未安装、连接失败还是其他调试问题。

解决方法是让评分直接启动 QEMU，通过串口文件收集结果，在出现内核监视器、QEMU 退出或超时后检查原有输出条件。构建失败会展示 `.grade-build.log`，QEMU 启动错误写入 `.qemu.out.err` 并显示，避免再次静默丢失证据。修改没有改变 `tools/test_lab4.c` 的断言、测试线程行为或三项各 10 分的判定条件。

修复后的脚本先在模拟 make/QEMU 环境中检查成功、缺失 Schedule 输出、启动失败、超时和构建失败五种路径，随后在实际虚拟机中得到三项 OK、总分 30/30。因此，最终分数来自真实内核运行，不是驱动模拟结果。

### 7.3 代码审查修正 Sv39 页表规则与旧框架不一致

原页表 walker 的中间项带 U，页表自检也要求根表项带 U。这种写法不适用于当前 Sv39 非叶子项约束。修正时将中间项改为仅带 V，并把相应自检改为验证 U/A/D 和 R/W/X 为零；用户访问权限由叶子项表达。不是取消检查，而是使断言与当前体系结构一致。

另外，`perm=0` 若直接形成只有 V 的所谓“数据页叶子”，并不能表达普通叶子映射；W 而无 R 的组合也有编码问题。因此在本实验接口中将零权限参数归一化为只读，写权限补读权限，并预置相应 A/D。这些属于代码审查和兼容性修正，不将其写成虚拟机已经实测出现过的每一种异常。

### 7.4 代码审查修正 大页遍历与高地址检查

启动根表包含 1 GiB 叶子，直接按普通下级页表遍历会把映射的数据错误解释为页表内容。解决方法是明确 walker 只支持 4 KiB 叶子，并新建根表完成内核重映射。与此配套，链接脚本按页对齐不同权限段，保证地址空间切换期间代码和栈仍然有效。

原 `check_boot_pgdir` 用 int 保存高地址起点，与 64 位地址范围不匹配，可能使循环未按预期验证实际映射。修正为用 `uintptr_t` 遍历从 `KERNEL_BEGIN_PADDR` 到受管理物理地址上界的页面，再检查相应高地址映射。这个问题说明“测试函数存在”不等于“测试覆盖了原本想覆盖的地址范围”。

分页启动还沿用了 lab3 中已经处理的临时恒等映射：开启 satp 时覆盖尚未跳到高地址的取指，跳转后撤销。该问题的处理承接前一实验，不冒充本次新出现的故障。

### 7.5 编译检查中发现的类型问题

对所有内核 C 文件进行目标语法检查时，发现 SLOB 的 `__slob_free_pages` 将整数形式的内核地址直接传给要求 `void *` 的 `kva2page`。通过显式转换恢复接口类型一致性。这属于编译检查发现的问题，不能只因某个版本的编译器允许警告就认为调用契约没有问题。

原评分代码另有 `void (*)(void *)` 的测试线程入口传给 `int (*)(void *)` 接口的 warning。此次虚拟机编译并未因此终止，评分中的测试线程也不返回。我们没有通过更改内核公开接口或测试断言消除该提示，并在宿主机检查注入后的测试文件时单独说明了该类型警告的放宽范围。

### 7.6 哪些输出不应当误判为 bug

链接器的 `removing unused section` 是当前启用未使用节清理后的正常提示，不代表函数源码被错误删除。部分函数可能被内联，或没有在本次镜像中被引用。

init 完成输出之后的 `process exit!!` 来自原 `do_exit`，当前没有实现完整退出回收，因此进入调试监视器是预期路径。但这不意味着可以忽略所有 panic：如果在必要自检和 init 输出之前出现断言失败或页访问异常，仍属于需要定位的错误。

## 九 实验知识点与 OS 原理的对应关系

| 实验知识点 | OS 原理中的对应概念 | 含义 关系与差异 |
| --- | --- | --- |
| 物理页描述符与 best-fit 分配 | 物理内存管理与外部碎片 | 分配器寻找能满足连续页数的最小空闲块，释放时合并相邻空闲块；它管理物理页，不直接决定进程虚拟地址布局，也不等于页面置换算法 |
| Sv39 三级页表与 get_pte | 分页与多级页表 | 通过分级索引节约未使用地址空间对应的页表存储；本实验建立 4 KiB 映射，不能由此推断已经实现任意大页拆分或缺页调入 |
| R/W/X/U 权限与分段重映射 | 地址保护与最小权限 | 代码 RX、只读数据 R、数据 RW，使不同用途的页面拥有不同访问权限；这里按链接段设置页权限，并不是硬件分段机制 |
| 页引用计数 | 共享资源生命周期管理 | 同一物理页可以由多个地址引用，最后一个受管理引用消失后才释放；该计数不是进程数量，也不是页面访问频率 |
| TLB 刷新 | 地址转换缓存一致性 | 页表内存修改后要使旧地址或权限缓存失效；当前按地址或整表刷新，不涉及多核 TLB shootdown |
| mm_struct 与 VMA | 逻辑地址空间管理 | VMA 描述合法半开区间，页表负责实际翻译，两者相互补充；本实验没有按 VMA 实现用户进程的按需分配 |
| proc_struct 与线程状态 | PCB 与进程状态模型 | PCB 汇集调度及资源信息；PROC_RUNNABLE 同时包含等待运行和正在运行的线程，不是教材中单独列出的“运行态”与“就绪态”两个枚举值 |
| 独立内核栈与共享页表 | 进程与线程的资源模型 | 每个线程保留自己的调用栈和现场，同时共享内核地址空间；与有独立用户页表的用户进程存在明显区别 |
| context 与 trapframe | 上下文切换与异常现场保护 | context 服务于函数边界上的线程切换，trapframe 服务于异常返回和首次现场构造；保存寄存器范围与恢复时机不同 |
| schedule 与 switch_to | 调度策略与切换机制 | 前者决定运行对象，后者实现 CPU 现场交接；更换调度策略不必重写全部寄存器保存代码 |
| 中断保护与资源发布 | 临界区与原子性 | 单核下屏蔽中断保护线程发布和切换关键步骤；这不等于多核互斥，也不能替代自旋锁或跨核内存同步 |
| idle 线程 | 空闲任务与统一调度 | 为没有普通可运行线程时提供合法运行对象，同时统一启动执行流；本实现持续检查调度标志，没有进一步实现低功耗等待策略 |

我们认为本实验最重要的联系是资源状态和 CPU 状态必须共同保持一致。只保存寄存器而不保证目标栈与页表有效，无法恢复线程；只将 PCB 设为可运行而没有构造正确返回现场，同样无法执行。由此，创建、映射与调度不是彼此独立的函数填空，而是有先后约束的系统状态转换。

## 十 OS 原理中重要但本实验尚未覆盖的内容

**用户态进程与系统调用。** 当前线程始终在内核态运行，没有用户程序装载、用户栈、系统调用参数检查和独立用户页表，因此没有验证用户与内核之间完整的保护边界。

**按需分页和页面置换。** 本实验采用预映射，没有缺页时分配数据页、访问硬盘后备存储、换入换出或基于访问历史的置换策略。虽然结构中保留了后续实验接口，并不代表这些功能已经实现。

**写时复制与一般地址空间复制。** `copy_mm` 只处理内核线程共享内核地址空间的限定情况，未实现 fork 用户空间复制，也没有只读共享后触发写故障的 COW 机制。

**抢占式调度与调度性能。** 当前没有时间片耗尽触发的抢占、优先级、动态反馈队列、实时期限或饥饿控制；两个测试线程都运行过也不能证明所有负载下的公平性和响应时间。

**多核并发同步。** 实测只有一个 HART。关闭本核中断不能阻止其他核心同时修改链表，因此多核下还需要锁、原子操作协议、内存顺序约束、CPU 亲和与负载均衡等机制。

**线程等待和完整生命周期。** 虽然定义了睡眠及僵尸状态，但没有实现完整的 wait、退出回收、孤儿进程处理及父子资源交接。当前退出 panic 也说明生命周期管理尚未闭环。

**进程间通信与同步。** 本实验不包含管道、消息队列、共享内存通信协议、信号量、条件变量及其阻塞唤醒过程，不能据此评价同步原语的正确性。

**设备 I/O 与文件系统。** 当前运行不需要磁盘镜像，没有文件描述符管理、持久化文件系统、阻塞 I/O 调度和完整设备驱动协作。

这些未覆盖内容界定了本实验的完成范围：已经建立内核线程运行与调度的基础，但距离具备完整资源隔离、并发同步和持久化能力的通用操作系统仍有后续模块需要实现。
